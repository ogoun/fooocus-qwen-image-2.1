# Fooocus-Qwen-Image-2.1 — спецификация

- **Дата:** 2026-09-21
- **Статус:** на вычитке у заказчика
- **Модель:** Qwen-Image-2.1 (7B в визуальной части), локальные веса

## 1. Цель

Оболочка в духе [Fooocus](https://github.com/lllyasviel/Fooocus) поверх локальной
модели [Qwen-Image-2.1](https://huggingface.co/Qwen/Qwen-Image-2.1). От Fooocus
берётся философия интерфейса — одна строка промта, одна кнопка, всё остальное за
переключателем «Продвинутое» — и список из 277 стилей. Внутренняя машинерия Fooocus
не переносится: она построена вокруг ограничений SDXL, которых у Qwen-Image-2.1 нет.

### 1.1. Обязательные возможности

1. Генерация изображений из текста.
2. Редактирование изображения промтом.
3. Редактирование изображения промтом по маске.
4. Сохранение и загрузка промтов.
5. Подключение к внешней LLM, галочка «AI буст», системный промт в файле.
6. Сохранение результата в PNG.

### 1.2. Согласованные дополнения

7. Галерея истории и запись параметров в метаданные PNG.
8. Outpaint — расширение холста.
9. До 10 референсных изображений с подписями-тегами промта.
10. Три пресета качества: LowQuality, MiddleQuality, MaxQuality.
11. Двуязычный интерфейс RU/EN.

### 1.3. Вне рамок первой версии

LoRA, ControlNet, апскейл отдельной моделью, wildcards, очередь заданий,
многопользовательский режим, аутентификация.

## 3. Проверенные факты о модели и API

Всё ниже прочитано в исходниках, а не в описаниях. Ссылки — на ветку `main`
diffusers, файл `src/diffusers/pipelines/qwenimage21/pipeline_qwenimage21.py`.

### 3.1. Доступность пайплайна

`QwenImage21Pipeline` есть **только в `main`** diffusers. В релизе 0.40.0 (последний
на PyPI) каталога `pipelines/qwenimage21/` нет. Требуется `transformers>=5.17`
(актуальный релиз 5.17.0). Устанавливаем diffusers из git **с фиксацией коммита** —
пакет неопубликованный, и без фиксации сборка невоспроизводима.

### 3.2. Сигнатура `__call__`

```
prompt, image, negative_prompt, true_cfg_scale=1.0, height, width,
num_inference_steps=40, sigmas, num_images_per_prompt=1, generator, latents,
prompt_embeds, prompt_embeds_mask, negative_prompt_embeds, negative_prompt_embeds_mask,
output_type="pil", return_dict=True, attention_kwargs, callback_on_step_end,
callback_on_step_end_tensor_inputs=["latents"], output_resolution=1024, use_kv_cache=True
```

Следствия:

- **`mask_image` отсутствует.** Маска подаётся не как отдельный канал, а как ещё одно
  условное изображение (раздел 6).
- `image` — **один плоский список** условных изображений на весь батч, вложенность
  запрещена явной проверкой. Значит при нескольких промтах с разными референсами
  пайплайн вызывается по одному разу на промт.
- `true_cfg_scale=1.0` по умолчанию, в докстринге: «Qwen-Image 2.1 is meant to be
  sampled without guidance». Негативный промт игнорируется, пока CFG не поднят выше 1.
- `output_resolution` (по умолчанию 1024) задаёт целевую сторону и размер, до которого
  масштабируются условные изображения. `height` и `width` при наличии `image`
  выводятся из соотношения сторон **последнего** изображения списка.
- Размеры принудительно округляются вниз до кратности 32 (`vae_scale_factor * 2`).
- `callback_on_step_end` даёт прогресс по шагам и доступ к `latents`.
- `use_kv_cache` кэширует ключи и значения текста и условных изображений после
  первого шага. В докстринге предупреждение: переключение флага меняет результат при
  одном и том же сиде, поэтому флаг фиксируется в метаданных.

### 3.3. Адресация референсов

`_get_qwen_prompt_embeds` строит шаблон, подставляя литералы `<image1>`, `<image2>`,
… перед каждым блоком зрения. Официальный `system_prompt_edit.txt` из репозитория
QwenLM это подтверждает и делает обязательным:

> For Multi-Image Input (N >= 2), the rewritten instruction MUST use `<image1>`,
> `<image2>`, ... to refer to each input image. Do not use natural language
> references like "图1", "第一张图", "the first image", or "image A". This tagging
> format is mandatory and non-negotiable. For single-image input (N = 1), do NOT use
> tags — refer to the image naturally.

Интерфейс обязан подписывать миниатюры ровно этими тегами и не подставлять теги при
единственном референсе.

### 3.4. Обработка RGBA

Для текстового энкодера альфа сводится на белый фон, для VAE передаются все четыре
канала. Модель нативно порождает и редактирует прозрачные изображения; рекомендуемая
формулировка промта — `This is an RGBA image with transparency. <описание>. The image
has alpha channel and the background is transparent.`

### 3.5. Кэширование эмбеддингов: ограничение публичного API

`__call__` вызывает `encode_prompt(...)` **не передавая** `image_pad_mask`, хотя
параметр у `encode_prompt` есть. Поэтому передать готовые `prompt_embeds` вместе с
`image` через публичный API невозможно — `encode_prompt` выбросит
`ValueError: Pass image_pad_mask alongside prompt_embeds…`. Кроме того `check_inputs`
запрещает одновременную передачу `prompt` и `prompt_embeds`.

**Решение:** не переопределять `__call__` (это скопировало бы около двухсот строк
цикла денойзинга и дало бы дрейф при обновлении diffusers), а переопределить
единственный защищённый метод `_get_qwen_prompt_embeds`. Он возвращает ровно
`(prompt_embeds, encoder_attention_mask, image_pad_mask)` **до** размножения на
`num_images_per_prompt` и до обнуления маски — идеальная точка кэширования.

```python
class QwenImage21StudioPipeline(QwenImage21Pipeline):
    def _get_qwen_prompt_embeds(self, prompt=None, image=None, device=None):
        key = self._cache.key(prompt, image)
        hit = self._cache.get(key)
        if hit is not None:
            return self._cache.to_device(hit, device)
        with self._residency.text_encoder_resident():
            out = super()._get_qwen_prompt_embeds(prompt, image, device)
        self._cache.put(key, out)
        return out
```

Переопределение занимает десяток строк, цикл денойзинга остаётся авторским,
перестановка моделей происходит ровно вокруг реального кодирования и полностью
пропускается при попадании в кэш.

### 3.6. Прочее, проверенное в коде

- `model_cpu_offload_seq = "text_encoder->transformer->vae"` — штатный порядок
  выгрузки, который мы заменяем своим (раздел 4).
- `AutoencoderKLQwenImage21.enable_tiling()` существует — нужен для 2K.
- Процессор внимания по умолчанию — `QwenImage21AttnProcessor` (без компиляции).
  `QwenImage21FlexAttnProcessor` быстрее на префилле, но требует `torch.compile`,
  иначе разворачивает плотную fp32-матрицу и падает по памяти. Оба идут через
  `dispatch_attention_fn`, то есть бэкенд внимания (flash/sage) выбирается штатно.
- `interrupt` читается в цикле денойзинга; прерывание выполняется установкой
  `pipe._interrupt = True` из другого потока, подмена `__call__` не нужна.

## 4. Решение 1: политика резидентности вместо квантования

### 4.1. Отклонённые варианты

| Вариант | Почему отклонён |
|---|---|
| GGUF (leejet) | Формат `stable-diffusion.cpp`; автор явно требует свой форк ComfyUI-GGUF вместо city96. В `diffusers/loaders/single_file_utils.py` есть маппинг `QwenImageTransformer2DModel` (версия 1.0) и **нет ни одного упоминания** `QwenImage21Transformer2DModel` — путь через diffusers закрыт. Принятие означало бы замену бэкенда на C++ бинарь без callback-ов и без гибкости. |
| Nunchaku INT4 (W4A4) | Квантует только DiT, Qwen3-VL остаётся bf16 (16.3 ГБ). На 4090 — 21.35 ГБ резидентно, и карточка модели прямо отмечает, что это ограничивает число референсов, то есть ломает требование 9. Ускорение ×1.84, отклонение LPIPS 0.231 к bf16. Требует `torch==2.12.1` и dev-сборку под cu13. |
| Квантование текстового энкодера (int8/NF4) | Освободило бы память, но Nunchaku намеренно оставляет энкодер в bf16 — сигнал, что деградация заметна. Трансформер потребляет сырые скрытые состояния энкодера, а не его текст. |
| Штатный `enable_model_cpu_offload()` | Гоняет около 32 ГБ по шине на **каждую** генерацию. При пресете LowQuality (~10 с) это до трети времени. |

### 4.2. Принятое решение

Всё в bf16, без потерь качества. Память решается размещением:

- **DiT (14.2 ГБ) и VAE (1.35 ГБ) резидентны в VRAM постоянно.** 15.6 ГБ занято,
  около 8 ГБ остаётся на активации, условные латенты и до 10 референсов.
- **Qwen3-VL (17.5 ГБ) живёт в закреплённой памяти хоста.** Поднимается в VRAM
  только при промахе кэша эмбеддингов, с временным вытеснением DiT. Пик при
  кодировании: 17.5 + 1.35 = 18.85 ГБ.
- **Кэш эмбеддингов** по ключу «промт, негатив, отпечаток списка референсов».
  Перебор сида, шагов, разрешения и числа изображений трафика по шине **не создаёт**.
- Смена промта или набора референсов стоит однократно около 3 с (17.5 ГБ вверх и
  14.2 ГБ обратно при PCIe 4.0 x16).

Закрепление памяти включается флагом `--pin-memory` (по умолчанию включено) с мягким
откатом на обычную память, если закрепить 17.5 ГБ не удалось.

`_execution_device` переопределяется и возвращает фиксированное устройство: при
ручном размещении модулей на разных устройствах штатная реализация может вернуть CPU.

### 4.3. Пресеты качества

Стартовые значения; уточняются `tools/benchmark.py` после сборки.

| Пресет | `output_resolution` | `num_inference_steps` | Расчётная оценка |
|---|---|---|---|
| LowQuality | 1024 | 16 | ~10 с |
| MiddleQuality | 1536 | 28 | ~30 с |
| MaxQuality | 2048 | 40 | ~75 с |

Расчёт: 2·7·10⁹·N_токенов FLOP на шаг при примерно 35 эффективных TFLOPS bf16. На
2048² последовательность — около 4100 позиций (VAE сжимает в 16 раз, затем упаковка
2×2), поэтому внимание здесь дешёвое и 2K достижим.

`image_number > 1` выполняется **циклом с разными сидами**, а не через
`num_images_per_prompt`: это держит пик VRAM плоским и даёт прогресс по каждой
картинке отдельно.

Необязательные ускорители, выключены по умолчанию, за «Продвинутым»:
`torch.compile` вместе с `QwenImage21FlexAttnProcessor`, выбор бэкенда внимания.

### 4.4. Соотношения сторон

Карточка модели приводит семь рекомендованных соотношений с точными размерами для
2K: 1:1 — 2048×2048, 4:3 — 2400×1792, 3:4 — 1792×2400, 3:2 — 2528×1696, 2:3 —
1696×2528, 16:9 — 2752×1536, 9:16 — 1536×2752.

Здесь есть расхождение, которое надо зафиксировать явно, иначе оно всплывёт как
случайное несовпадение размеров. Внутренняя функция пайплайна `calculate_dimensions`
считает стороны как `sqrt(площадь · отношение)` с округлением до кратности 32 и для
16:9 при `output_resolution = 2048` даёт 2720×1536, а не 2752×1536 из карточки.

**Принято:** канонический список — таблица из карточки модели. Размеры передаются в
`height`/`width` **явно**, а не выводятся пайплайном. Для пресетов ниже 2K стороны
пересчитываются с сохранением площади `output_resolution²` и округлением каждой
стороны вниз до кратности 32. Значение `output_resolution` при этом всё равно
передаётся: оно управляет масштабом, до которого приводятся условные изображения.

Отдельный пункт «от референса» оставляет `height`/`width` пустыми — тогда пайплайн
наследует соотношение последнего изображения списка, как описано в 3.2.

## 6. Решение 3: редактирование по маске

Официальный блог, раздел «Local Editing: Flexible Region Selection»:

> Circles and painted annotations obscure some of the original content. To preserve
> the complete input, Qwen-Image-2.1 also accepts **the original image and a separate
> mask as two inputs**.

То есть маска — это `image=[оригинал, маска]`. Машинерия Fooocus (`InpaintWorker`,
`fooocus_fill`, latent swap, патч inpaint-модели) существует лишь потому, что SDXL не
понимает маску семантически; здесь она не нужна. От Fooocus берётся только UX: кисть,
растушёвка, режимы работы с областью.

Источник данных — `gr.ImageEditor`, который возвращает
`{background, layers, composite}` (проверено интроспекцией Gradio 6.5.1).

### 6.1. Режимы

| Режим | Что уходит в модель | Когда применять |
|---|---|---|
| **Маска** (по умолчанию) | `[оригинал, ч/б маска]`; маска строится из альфы слоя кисти | Обычное локальное редактирование, оригинал не искажается |
| **Аннотация** | `[composite]` — изображение с цветными пометками | Несколько областей сразу, разные инструкции по цветам в одном промте |
| **Точная область** | `[кроп оригинала, кроп маски]`, затем вклейка | Мелкая деталь на большом холсте |

Режим «Аннотация» даёт возможность, которой в Fooocus нет: пометить области разными
цветами и одним промтом задать разные правки — «убрать часы в синем круге, волосы в
красном сделать чёрными, область в зелёном заменить на серую льняную пижаму».

### 6.2. Гарантия сохранности

Поверх любого режима результат склеивается с оригиналом по растушёванной маске: вне
маски пиксели остаются побайтово исходными. Радиус растушёвки — ползунок, галочка
«склеивать с оригиналом» отключает поведение для случаев, когда правка должна
затронуть весь кадр.

Маска перед подачей в модель проходит бинаризацию, необязательное морфологическое
расширение (ползунок «запас») и сглаживание края. Для режима «Точная область» bbox
маски расширяется контекстным запасом, приводится к размерам, кратным 32, и после
генерации вклеивается обратно с той же растушёвкой.

### 6.3. Outpaint

Холст расширяется на выбранные стороны на заданную долю, исходное изображение
вклеивается на место, новая площадь становится маской, дальше — режим «Маска».

## 7. Решение 4: референсные изображения

- До 10 слотов, порядок значим и соответствует `<image1>`…`<image10>`.
- Миниатюры показаны в главном окне, **каждая подписана своим тегом**.
- Миниатюры **подписаны** своим тегом; вставку тега в промт делает пользователь
  вручную. Gradio не даёт программного доступа к позиции курсора в текстовом
  поле, поэтому «вставить тег по клику в место курсора» нереализуемо в
  принципе — подпись под миниатюрой достигает той же цели (пользователь видит,
  каким тегом адресовать какое изображение) без этого доступа. Требование
  заказчика — подписи миниатюр — выполнено; см. раздел «Отступления».
- При одном референсе теги не используются — по требованию 3.3.
- Слоты переставляются и удаляются; удаление перенумеровывает подписи.
- Соотношение сторон результата по умолчанию наследуется от последнего референса —
  так устроен сам пайплайн; в UI это показано явно и переопределяется.

## 8. Решение 5: внешняя LLM и AI-буст

### 8.1. Подключение

По образцу `I:\ASR_LLM_TTS`: OpenAI-совместимый клиент на stdlib `urllib`, без
тяжёлых зависимостей. Файл `llm_endpoint.txt` того же свободного построчного формата
(имя бэкенда, хост с портом или без, `token=…`), порядок строк не важен, комментарии
через `#`. Кнопка «Проверить связь» опрашивает `/v1/models`.

### 8.2. Системные промты

Файлы в `resources/prompts/`, правятся пользователем, перечитываются при каждом
запросе (правка без перезапуска):

| Файл | Источник | Формат ответа |
|---|---|---|
| `system_prompt_t2i.txt` | QwenLM/Qwen-Image-2.1 | `{"rewritten_prompt": "...", "wh_ratio": "3:2"}` |
| `system_prompt_edit.txt` | QwenLM/Qwen-Image-2.1 | `{"rewritten_prompt": "...", "wh_ratio": "...", "ratio_follow": "<image1>"}` |
| `system_prompt_describe.txt` | наш | свободный текст |

Два следствия, которые нужно донести до интерфейса:

1. T2I-переписыватель **всегда отвечает по-английски**. Пользователь пишет промт
   по-русски и получает корректный английский — отдельный переводчик не нужен.
2. Ответ содержит соотношение сторон. При включённом AI-бусте оно подставляется в UI
   автоматически, с возможностью отменить.

Официальные промты писались под дообученную `Qwen-Image-2.1-PE-T2I`. Обычная модель
может вернуть не-JSON — тогда берём текст как есть и пишем предупреждение в журнал, а
не роняем генерацию.

### 8.3. Поведение галочки «AI буст»

Исходный и переписанный промт показываются оба; переписанный редактируется вручную
перед генерацией. В метаданные PNG пишутся оба.

## 9. Решение 6: стили, промты, метаданные, галерея

### 9.1. Стили

277 стилей из шести JSON-файлов Fooocus, формат `{name, prompt с {prompt},
negative_prompt}`. Множественный выбор, порядок применения — как в Fooocus.

**Оговорка, обязательная к отображению в UI:** при `true_cfg_scale = 1.0` (значение
по умолчанию, и модель на него рассчитана) негативная часть стилей и негативный промт
**не действуют**. Без подсказки это выглядит как неисправность.

### 9.2. Библиотека промтов

Именованные пресеты JSON в `user/prompts/`. Сохраняются промт, негативный промт,
выбранные стили, пресет качества, соотношение сторон, сид и все продвинутые
параметры. Загрузка восстанавливает состояние UI целиком.

### 9.3. Метаданные PNG

Все параметры пишутся в `tEXt`-чанки при сохранении; перетаскивание PNG в окно
восстанавливает параметры. Схема ключей фиксируется в `docs/ARCHITECTURE.md` и
включает версию приложения, версию diffusers, исходный и переписанный промт,
негативный промт, стили, сид, шаги, разрешение, `output_resolution`,
`true_cfg_scale`, `use_kv_cache`, режим маски, список референсов и время генерации.

`use_kv_cache` фиксируется обязательно: по докстрингу пайплайна его переключение
меняет результат при том же сиде.

Сохранение — всегда PNG, с поддержкой RGBA.

### 9.4. Галерея

История по каталогам дат, превью, повторная загрузка параметров, открытие каталога в
проводнике, удаление.

## 10. Интерфейс

Gradio 6.5.1 (зафиксирован), `gr.Blocks`. Слушает `0.0.0.0:7865` по умолчанию.

Компоновка в духе Fooocus: широкая область результата, под ней строка промта и кнопка
«Сгенерировать», справа — панель, свёрнутая до пресета качества и соотношения сторон,
раскрываемая чекбоксом «Продвинутое» до стилей, негативного промта, сида, шагов, CFG,
режима маски и ускорителей.

Вкладки: «Генерация», «Редактирование», «Галерея», «Настройки».

Прогресс по шагам — через `callback_on_step_end`. Кнопка «Прервать» ставит
`pipe._interrupt = True`. Показывается занятая VRAM и состояние кэша эмбеддингов.

Двуязычность — словарь `ui/i18n.py`, переключатель в шапке, выбор запоминается.

## 11. Установка и запуск

`install.ps1` и `install.sh` выполняют одинаковые шаги:

1. Создать `.venv` (Python 3.12, откат на 3.13), обновить pip, setuptools, wheel.
2. **Сначала** `torch` и `torchvision` с индекса
   `https://download.pytorch.org/whl/cu128`.
3. Остальные зависимости из `requirements.txt`.
4. Перепроверить, что `torch.__version__` содержит `cu`, иначе переустановить
   принудительно: сторонние пакеты способны подменить CUDA-сборку на CPU-сборку.
5. Контроль готовности: импорт `QwenImage21Pipeline`, проверка наличия весов и
   доступности CUDA. «Установилось» должно означать «запустится».

Состав `requirements.txt`:

```
torch, torchvision                       (ставятся отдельно, с индекса cu128)
diffusers @ git+https://github.com/huggingface/diffusers@cc8644b447d8f11074d3df06d0ee0e3e7c91bf75
transformers>=5.17
accelerate
safetensors
huggingface-hub
tokenizers
protobuf
Pillow
numpy
opencv-python-headless

einops
```

`run.ps1` и `run.sh` проверяют наличие и работоспособность `.venv`, предупреждают об
отсутствии CUDA и запускают `python -m fooocus_qwen --host 0.0.0.0 --port 7865`. Все
аргументы прокидываются в приложение как есть.

## 14. Отступления

Раздел добавлен по итогам реализации (задача 15). Перечислены все места, где
поставленная система отличается от того, что написано выше, вместе с причиной
расхождения. Источник истины при расхождении — код и `docs/ARCHITECTURE.md`,
которые описывают систему как она построена, а не как она планировалась.

1. **Подписи миниатюр вместо вставки по клику** (раздел 7). Gradio не даёт
   программного доступа к позиции курсора в `gr.Textbox`, поэтому «клик по
   миниатюре вставляет тег в позицию курсора» нереализуемо буквально.
   Реализовано: каждая миниатюра референса подписана ровно тем тегом
   (`<image1>`, `<image2>`, …), которым промт должен на неё ссылаться;
   вставку в текст промта пользователь делает сам. Требование заказчика —
   подписи, которые снимают необходимость угадывать нумерацию, — выполнено.

2. **`region_box` может вернуть прямоугольник не кратный 32** (раздел 6.2).
   Спецификация требует приводить bbox режима «Точная область» к размеру,
   кратному 32. Реализация (`imaging/masking.py::region_box`/`_snap_span`)
   делает это, только если кратное окно, вмещающее маску и контекстный запас,
   помещается в холст целиком; если не помещается — отдаётся холст целиком,
   и тогда его размер может быть не кратен 32. Причина: округлить вверх до
   кратности значило бы либо обрезать часть нарисованной пользователем
   маски (недопустимо — маска обязана попасть в вырезку полностью), либо
   выйти за границы изображения. Компенсация: конвейер и так сам приводит
   условные изображения к разрешению пресета, а `stitch()` умеет вклеивать
   патч любого размера обратно в исходный прямоугольник, так что
   некратность краевого случая не ломает результат — только не даёт
   бонуса «модель дорисовывает ровно по границе кратности».

3. **Ось, которую outpaint не расширяет, сохраняет точный исходный размер**
   (раздел 6.3). Спецификация не оговаривала это явно, но естественное
   прочтение «округлить холст до кратности 32» могло бы означать округление
   обеих осей. Реализовано (`imaging/outpaint.py::plan`): к кратности 32
   приводится только та ось, которую действительно расширяют; ось, для
   которой не выбрана ни одна сторона расширения, остаётся ровно исходного
   размера. Причина: округление неактивной оси в любую сторону либо сузило
   бы холст относительно оригинала (переполнение при вставке), либо
   расширило бы сторону, которую пользователь не просил трогать, без
   всякой пользы — новая полоса всё равно не заполнена содержимым.

4. **Сентинел «наследовать размер от источника» — `aspect.FOLLOW_REFERENCE`,
   а не неявное `"1:1"`** (разделы 4.4 и 7). Ранняя редакция реализации
   действительно использовала пустое значение/`"1:1"` как признак «размер не
   выбран», из-за чего осознанный выбор квадратного кадра при правке был
   неотличим от «пользователь ничего не выбирал» и молча приводил к тому же
   поведению. Заменено на отдельный именованный сентинел
   `aspect.FOLLOW_REFERENCE` (строка `"от референса"` в списке соотношений
   UI), который `Generator.resolve_size` проверяет явно. Побочный эффект:
   `ConditionSlot`/метаданные PNG хранят `width`/`height` как `None` именно
   в этом случае, а не как числа, выведенные пайплайном постфактум.

5. **Тайминги пресетов качества не те, что были оценены** (раздел 4.3).
   Оценка строилась на 35 эффективных TFLOPS bf16 и давала ~10/30/75 с для
   LowQuality/MiddleQuality/MaxQuality. Единственный измеренный на этой
   машине пресет — LowQuality, 1024 px, 16 шагов — занял 36.84 с (из них
   разовая перестановка энкодера ~3 с), то есть в 3.7 раза больше оценки.
   `MiddleQuality` и `MaxQuality` не измерены ни разу: их оценки, построенные
   на той же (опровергнутой для LowQuality) модели производительности,
   ненадёжны в ту же сторону и не подтверждены. Бенчмарк
   `tools/benchmark.py`, которым раздел 12.2 предполагал уточнить эту
   таблицу, не реализован — измерение отложено до появления свободной
   видеокарты; статус зафиксирован в `docs/SMOKE.md`.

6. **Измеренные веса моделей ниже оценённых** (раздел 2). Оценка: `transformer`
   14.2 ГБ, `text_encoder` 17.5 ГБ. Измерено приложением по факту загруженных
   тензоров: 13.3 ГБ и 16.3 ГБ соответственно. Направление то же (энкодер
   тяжелее трансформера), архитектурное решение раздела 4.2 не меняется —
   зазор до 24 ГБ видеопамяти при резидентном энкодере только увеличивается.

7. **Каталог `resources/presets/*.json` не реализован** (раздел 5). Структура
   проекта предполагала пресеты качества как отдельные JSON-файлы. Реализовано
   как таблица `PRESETS: dict[str, QualityPreset]` прямо в
   `engine/presets.py` — трёх записей достаточно, они меняются только при
   пересмотре тайминга по замерам (пункт 5 этого раздела), и заводить под них
   файловый формат с загрузчиком и валидацией — избыточная косвенность на
   данном этапе. `config.PRESET_DIR` объявлен на случай будущего переноса в
   файлы, но в текущем коде не используется.

8. **`imaging/annotate.py` не выделен отдельным модулем** (раздел 5). Вся
   содержательная работа режима «Аннотация» — свести слои редактора в одно
   изображение с цветными пометками — покрывается методом `PIL`
   `Image.alpha_composite`, который использует значение `composite`, отданное
   самим `gr.ImageEditor`. Реализовано прямо в `ui/tab_edit.py::collect()`;
   отдельный модуль на пять строк не заводился, чтобы не плодить структуру
   ради структуры. Подробнее — `docs/ARCHITECTURE.md`, раздел 1.

9. **`tools/benchmark.py` не реализован** (раздел 12.2). Измерение времени
   шага, пиковой VRAM и времени перестановки моделей для трёх пресетов и для
   1/5/10 референсов требует видеокарты, которая на момент задачи 15
   намеренно оставлена свободной. Вместо автоматизированного бенчмарка в
   `docs/ARCHITECTURE.md` и `docs/SMOKE.md` зафиксированы числа, измеренные
   вручную при разработке (раздел 4.3 этого документа, пункт 5 выше), с явной
   пометкой, что три из них (кроме LowQuality) не измерены.
